# `prompt_equivalence/` — the step-9 gate record

`prompt_equivalence_v1.json` is the evidence for Phase 2 **step 9**: the one-time
prompt-equivalence test that gates step 10.

`experiments/routegate_routing/extract_routing_v1.py` still imports the
historical `rq3_dev_generation` module for its model, tokeniser and
chat-template configuration. Replacing that import with `routegate.runtime`
changes a GPU code path that cannot be validated by re-running it offline, so
this record is the proxy.

Each of the 480 development prompts is rendered through **both**
`build_chat_strict` implementations — the historical one and
`routegate.runtime`'s — and the two renderings are compared as UTF-8 bytes. Each
rendering is then tokenised with the **same** pinned tokeniser, using the same
call the frozen extraction makes: `tokenizer(text, return_tensors=...)` with
`add_special_tokens` left at its default, never overridden. That matters — the
extraction does not override it, so a comparison that did would be evidence
about a call the extraction never performs. The step-9 helper differs from the
extraction in exactly one respect: `return_tensors=None` returns plain lists
rather than torch tensors, which keeps this stage off the tensor framework and
changes no token id.

Both renderings must be identical byte for byte, and both tokenisations
identical in full `input_ids`, attention mask, attention-mask length and final
prompt token — 480/480 on every one.

Unlike `pilot_reference/`, this is **not a promoted artifact** — nothing was
copied from another workspace. It is generated by
`tools/migration/prompt_equivalence_check.py`, which takes the legacy module and
the manifest as explicit arguments so no machine path is written into committed
code.

## What it records, and what it deliberately does not

Recorded: the verdict, the seven check results, the compared and mismatch
counts, SHA256 of the legacy module / `routegate/runtime.py` / the extraction
manifest, the model and revision, the resolved snapshot commit, the
tokenizer-config and chat-template digests, two aggregate ordered digests, and
the Python / transformers / tokenizers versions.

Not recorded, by design: prompt text, rendered text, token IDs, individual
per-row hashes, response text, absolute machine paths, and anything that would
locate held-out material. The two aggregate digests are what make the result
auditable without any of that — each is a SHA256 over the newline-joined,
row-ordered list of per-row digests, so it is order-sensitive and a single
changed prompt changes it, while storing no row-level fingerprint of the corpus.

If a mismatch ever occurs, the row **positions** go to a private failure log
outside the repository, never here.

## Re-verifying it

```
python tools/migration/prompt_equivalence_check.py \
    --legacy-module <path to rq3_dev_generation.py> \
    --manifest <path to the development extraction manifest.csv>
```

Offline, CPU-only, tokeniser from the local cache. `HF_HUB_OFFLINE` and
`TRANSFORMERS_OFFLINE` are set to `1` by the program itself — assigned, not
defaulted, so an inherited `0` cannot put the run back on the network — and the
outbound-connection guard is installed unconditionally at import, before
anything can reach Hugging Face. There is no flag to switch either off. No model
is instantiated and no GPU is used.

The expected SHA256 of the external manifest comes only from the committed
`manifests/development_inputs.json`; there is no override, so the gate cannot be
argued out of. A `--failure-log` path is resolved and refused up front if it
lands inside the repository.

A partial pass is a failure. There is no "480 minus a few" outcome that
authorises step 10.
